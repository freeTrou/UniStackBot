# 内部总线选型论证：插值器以下链路不采用 UDP · 文献证据版

> 状态：草稿 v0.3，供审核（2026-09-14：v0.2 插值器定律；v0.3 根因公理入 §0）。
> 引用经检索核实；置信度分级标注见 §7。
> 命题服务于《总线选型讨论纪要》：CAN FD 定版决策的文献支撑材料。

## 0. 命题的精确表述

**对象与分层**：本文讨论 Linux 运动控制栈的**内部链路**：

```
RL/控制器（50~200Hz）
   ↓
插值层（Linux 上的 JTC/插值器，500Hz~1kHz）
   ↓
底层总线 ←—— 本文论证对象
   ↓
MCU（可选中转）→ 电机
```

与**对外接口**（Unitree DDS/SDK 等开发者入口，位于 RL **之上**）严格区分——
外部入口的传输选择不触及栈内运动控制链路，对本命题不构成任何方向的论据。

**两条判据（同一把尺子的两种读法）**：

1. **晚到的物理定价**：链路消息晚到 2ms，物理结果是零、劣化、还是错误；
2. **插值器位置（操作性判据）**：插值器的输出是**节拍同步设定值**——tick N 的值
   晚到 = 插值时间轴漂一拍——所以**插值器住在哪一层，确定性就必须提供到哪一层**。

按拓扑与插值器位置落位：

| 形态 | 插值器位置 | 链路 | 晚到定价 | UDP |
|---|---|---|---|---|
| Linux→电机（直连） | Linux | 唯一链路 | 错误（控制环穿过它） | ❌ |
| Linux→MCU→电机 | Linux | 上联（节拍设定值流） | 非零（插值时间轴漂移） | ❌ |
| Linux→MCU→电机 | Linux | 末段 | 错误（伺服节拍所在） | ❌ |
| Linux→MCU→电机 | **下沉 MCU** | 上联（50~200Hz 参考流） | ≈0（MCU 取最新+本地插值吸收） | ✅ |

表中定价为"错误/非零"的行即**环内链路**（控制环或其时间轴穿过该线）。

**命题**：在插值器以下的链路（直连唯一链路、中转末段、以及插值器仍在 Linux 时的
上联）选用无构造性最坏情况上界的信道（UDP 及统计复用体系），无法支撑时序预算——
这不是参数调优问题，是**保证类别与后果类别不匹配**的结构问题。

**核心定律（可操作形式）**：**插值器下沉进 MCU 的那一刻，上联才获得 UDP 资格；
插值器留在 Linux 的每一天，插值以下的链路都需要构造性信道。** 主流方案把插值器
留在 Linux（JTC/ros2_control 生态、算法在用户态迭代最方便），所以主流底层总线是
CAN FD；产品化形态把插值器下沉进 MCU，门内之上才出现 UDP/以太网——市场分布
与本定律精确同构。

**根因公理（第一性原理）**：以上全部判据（定价、插值器位置）追到底是一条公理——

> **控制链路设计公理：最坏延迟必须是"自己的设计量"的函数，而不是"环境量"的函数。**
> 凡是延迟公式里出现别人的变量，那条链就没有进入设计权限——只能实测验收，不能设计证明。

| 链路 | 最坏延迟 = f(?) | 产权 |
|---|---|---|
| CAN | f(帧集合)——WCRT 闭式公式 [5][6] | ✅ 全产权，事前可证 |
| EtherCAT | f(调度表)——周期公式 [7][8] | ✅ 全产权 |
| UDP + 交换机 | f(共流、队列、两端调度器) | ❌ 产权旁落，事后统计 |
| TSN | 门控表自有；端点栈仍是别人的 | ⚠️ 半产权 |

公理的物理根源是**冲突解决方式**：CAN 用物理层仲裁把冲突变成有界的优先级顺序，
EtherCAT 用轮询调度消灭冲突，交换以太网用 FIFO 排队把冲突变成**无界延迟**——
"你的最坏时间是别人的函数"。两条根因独立可拆验证：**中段**（交换机排队）与
**两端**（时序住在软件栈里，归统计分时调度器管辖——直连无交换机时抖动仍在
0.1~2ms，实测见 §3）；TSN 只修复中段。最深一层是设计目的互为镜像：**数据网络
优化"不丢"（用缓冲吸收冲突），控制网络优化"不迟"（用仲裁/调度消除冲突）**——
UDP 不是做得不好，是基因为另一个目的而写。

## 1. 控制理论证据：稳定性分析要求"界"，且时变延迟比常值延迟更苛刻

网络化控制系统（NCS）文献三十年积累的核心结论，直接构成本命题的理论基础：

| 结论 | 出处 | 要点 |
|---|---|---|
| 网络-induced 延迟存在**稳定性上界**（MADB/MATI） | Walsh et al. 2002（被引 2600+）[1] | 超过最大允许传输间隔/延迟界，Lyapunov 意义下不稳定——**延迟不是性能问题，是稳定性问题** |
| 网络类型选择直接决定控制性能 | Lian, Moyne, Tilbury, IEEE TCST 2002（被引 800+）[2] | 网络的延迟特征（有界/无界、常值/时变）是分布式控制设计的**一等输入**，不是事后细节 |
| **时变延迟比常值延迟显著更苛刻** | Cloosterman et al. 2007 [3]；Liu et al. 2019 综述 [4] | 常值延迟可折算相位裕度损失（可设计）；时变/随机延迟使闭环动态不确定，稳定域收缩——**抖动比延迟本身更糟** |

**推论**：控制工程师分析环内链路时需要两样东西——**最坏情况界**（做稳定性预算）和
**时变性刻画**（做鲁棒性预算）。UDP 体系两样都给不了（§2），这不是"快不快"的问题。

**诚实脚注**：Lian/Moyne/Tilbury 2001 年 IEEE CSM 的实测对比 [2'] 针对的是**共享介质
半双工以太网**（CSMA/CD 碰撞域）——现代交换式全双工以太网已消除碰撞。该文引用价值
在于"控制学界正式评估过将以太网用于控制回路，并确认需要确定性机制"，而非其具体
碰撞数据；现代论证的重心已转移到**交换机排队 + 端点软件栈**（见 §3）。

## 2. 可证性证据：CAN/EtherCAT 有闭式最坏情况分析，UDP 体系没有

| 信道 | 最坏情况分析 | 文献地位 |
|---|---|---|
| CAN | **WCRT 闭式公式**（固定优先级响应时间分析） | Tindell, Burns, Wellings 1995（被引 880+）[5]；Davis et al. 2007 修正版 [6]——工业 CAN 时序验证工具的理论基础，**分析链条经过学术界三十年锤炼（含纠错）** |
| EtherCAT | 轮询周期时间公式；实验验证 | EtherCAT-over-TSN 实验评估（Springer 2025）实测 **100µs 周期、微乎其微的抖动** [7]；仿真分析（IFIP Networking 2021）[8] |
| UDP/交换以太网 | **无闭式上界** | 要获得界必须叠加 TSN 全套（802.1Qbv 门控/Qbu 抢占/AS 对时）——见 §4；TSN 综述 [9][10] |
| "实测置信度" | p99/p99.9 统计 | 不构成证明：换机/换负载/换软件版本即失效，无法写入稳定性分析 |

**要点**：Tindell 一系文献的存在本身就是判据——CAN 的最坏情况**先于部署可在纸面算出
并通过deadline 检查**；UDP 体系的"最坏情况"只能事后统计。前者可以进验收报告的证明栏，
后者只能进附录的测量记录栏。

## 3. 软件栈实测证据：UDP 体系的抖动住在端点栈里，链路只是小头

反方常辩："线上的 UDP 只有几微秒，很快。"——正确的回应是拆抖动成分：
UDP 端到端抖动 = 端点协议栈 + 排队（交换机）+ 线上（µs 级，可忽略）。
**不确定性的主要居所是软件栈，而软件栈恰是 UDP 体系无法绕开的部分。**

实测文献：

| 实测 | 出处 | 数据 |
|---|---|---|
| ROS 2 管线端到端延迟 | Barkhausen Institut, arXiv 2101.02074 [11] | ROS 2 抽象层引入**最高 50% 延迟开销**（相对裸 DDS）；实时内核显著降低抖动——**抖动主源在软件栈，证实栈即居所** |
| ROS 2 倒立摆控制环抖动 | Nuñez et al. [12] | GPOS 与 RTOS 下 ROS 2 控制环抖动对比，通用 OS 抖动不可用 |
| rclpy 软实时评估 | Barkhausen Institut [13] | Python 绑定在 Raspberry Pi 级平台不满足实时 |
| ROS 2 实时支持综述 | arXiv 2601.10722 [14] | 汇总社区实测：DDS 中间件性能随平台差异大、Pi 级平台抖动显著 |

**生态自证**（设计立场而非论文）：ros2_control 框架核心设计即**拒绝在控制环内使用
topic（DDS/UDP 族）**，采用接口内存直通——官方文档给出的理由就是高频下中间件延迟
抖动。框架架构本身是一次投了票的实测结论。

## 4. 标准史证据：工业三十年对"以太网做控制"的三次投票

1. **第一票（1990s~2000s）**：评估标准以太网+UDP/IP 用于控制回路 → 结论是否定的
   （[2'] 的时代背景）→ 催生改造路线。
2. **第二票（2000s）**：所有工业实时以太网协议（EtherCAT、PROFINET IRT、SERCOS III、
   Powerlink）**无一例外绕开标准 UDP/IP 栈**取确定性——保留以太网的线，删掉以太网的栈。
   若裸 UDP 可胜任环内链路，这四个协议没有存在的理由。
3. **第三票（2012~）**：TSN 标准体系（802.1Qbv/Qbu/AS/CB）——IEEE 用十余年标准化
   "给以太网补确定性"——**标准组织正式认定统计复用以太网缺乏控制域所需保证**，
   且修复成本 = 整套标准 + 交换机/端点硬件协同 [9][10]。

音频工程界同构：AES67/AVB 不是裸 UDP，而是 PTP 对时 + 整形后的 UDP——UDP 最成功的
实时应用都先行补上了它缺的保证层。

## 5. 反方论点与处置（论证完整性）

| 反方 | 处置 |
|---|---|
| "TSN 已把以太网修好" | TSN = 给以太网装总线纪律，**恰好证明裸 UDP 不行**（承认 TSN 即承认命题）；且 TSN 主要治理中段排队，**端点协议栈的抖动居所仍在**（§3 实测），Orin 级端点 NIC 支持残缺 |
| "那是 Linux/软件问题，不是 UDP 问题" | UDP 作为**系统**的抖动成分里，线上只占 µs 级；"UDP 很快"宣传的只是可忽略的成分。以"换更好的栈"回应，等于承认工程量花在追界上——而这正是 CAN/EC 用硬件白送的东西 |
| "平均延迟更低" | NCS 文献结论：稳定性由**界与时变性**决定，不是均值（§1）[1][3]。均值 50µs+尾 5ms 在 1kHz 环内劣于均值 180µs+尾 600µs |
| "市面有人形在用 UDP" | 位置误认：可查证案例（Unitree/Booster DDS）位于 **RL 之上的对外开发者入口**，不触及栈内"插值→总线→电机"链路——对本命题既非反例亦非正例；栈内链路的可查证据仍全部指向 CAN 族/EtherCAT（§4、[15]） |

## 6. 结论

> **信道选择律：保证等级必须匹配后果等级。** 后果等级以"晚到的物理定价"度量，
> 其操作性判据是插值器位置——**确定性必须覆盖到插值器所在层以下**。
> 插值器留在 Linux（主流形态）：插值以下的链路（直连唯一链路、中转上联与末段）
> 要求构造性保证信道（CAN：WCRT 可算 [5][6]；EtherCAT：周期可证 [7][8]）；
> 插值器下沉 MCU（产品化形态）：上联退化为参考流，统计信道（UDP）合法且最优——
> **搬走的是插值器，不是信仰**。
>
> UDP 在插值器以下链路不科学的完整表述：它把一个**只能事后统计**的信道，用在了
> **必须事前证明**的位置——理论（§1）、可证性（§2）、实测（§3）、标准史（§4）
> 四层证据同向。
>
> 公理收口：**CAN/EtherCAT 把最坏情况写进硅里卖给你，UDP 把最坏情况押在环境里
> 让你赌。控制设计者的工作只有两种：把赌注换成产权，或者换一条链。** 本工程的
> 落地选择：CAN FD 定版（全产权）；插值器下沉之日，即上联"换租为买"的评估之日。
